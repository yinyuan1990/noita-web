0 · 一句话总纲 Falling Everything

Noita（芬兰语"女巫"）由三个人的 Nolla Games 做出来，引擎叫 Falling Everything，从 2007 年前后的"落沙"原型一路演化了十几年。 它的全部设计可以压成一句话：世界里的每一个像素都是一格真实的材质，所有玩法都是这些材质按规则互相作用的结果。

围绕这句话，原版有四根支柱，后面每个模块都能对上其中一根或几根：

① 一切皆像素

地形、水、油、火、血、木箱、尸体、金块——全是材质格子。没有"贴图假象"，火能烧到的一定是真木头，血一定能流进水里。

② 数据驱动

469 种材质、328 条反应、316 个生物、482 张法术卡，全部写在 xml / lua 里。引擎只提供通用系统（元胞自动机、Box2D、组件更新器），内容由数据拼出来。

③ 组合而非枚举

法术是"卡牌组合"，反应是"标签配对"，状态是"沾了什么材质"。设计者写的是少量正交规则，玩家玩到的是它们相乘出来的无穷可能。

④ 确定性随机

同一个种子 → 同一个世界，任何位置的随机都从坐标派生（SetRandomSeed(x,y) / ProceduralRandom(x,y)）。存档只记"改过的区块"，别的重新算一遍就是。

生活比喻 Noita 更像一间化学实验室 + 沙盘，而不是一部剧本电影。设计师没有写"油桶被打中会爆炸"这句剧情，他只写了"油是可燃液体""火点燃可燃物""桶漏了油会流出来"， 然后爆炸是玩家自己在沙盘里"发现"的。做菜也一样：菜谱不写每一道菜，写的是"盐是咸的、油能炸、火会烧"，剩下的交给厨师去组合。

③ 到底什么意思：用公式和代码把"组合而非枚举"说透

数学角度：加法成本，乘法产出

枚举：要 N 个效果就写 N 份东西。成本 N，产出 N。
组合：把内容拆成几个独立维度，每个维度 ni 个选项，再写一条"怎么组合"的规则。成本是各维度加起来，产出是各维度乘起来：

成本 = n₁ + n₂ + … + nk　　　产出 = n₁ × n₂ × … × nk

例 1 · 材质反应（标签配对）：469 种材质两两相遇 ≈ 11 万对。枚举要写 11 万条。Noita 写 328 条，每条左边是标签（一个材质集合）而不是材质名：[meltable] + lava → [meltable]_molten。 一条规则覆盖 |A|×|B| 对。我们的实现里 328 条标签规则加载时展开成 10872 条具体 (a,b) 规则，杠杆约 33 倍。

例 2 · 火（属性判定）：火根本不走反应表，它是一条对所有材质成立的函数：

ignite(火, 邻格) = burnable(邻格) ∧ autoignition(邻格) ≤ fireTemp(火)

新加一种材质"纸"只填两个数，不写规则。枚举法加第 N+1 种材质要补它和前面 N 种的全部交互（O(N)，总共 O(N²)）；属性法加一种是 O(1)，总共 O(N)。

例 3 · 法术（函数复合）：每张修饰卡是一个函数 mi: Config → Config，弹丸卡是"用当前 Config 发一发"，施法就是复合：

shot = P( mk ∘ … ∘ m₁ ( c₀ ) )

482 张卡里约 300 张弹丸、179 张修饰。一根"1 弹丸 + 2 修饰"的杖，不同结果约 300 × 179 × 178 ≈ 950 万种；写的数据只有 482 条。设计者写加法，玩家玩到乘法。

程序角度：不是没有 if，是 if 判的东西从"名字"换成了"属性"

常见的 Unity 写法——每个效果一个 prefab，脚本里按名字分支：

// Fireball.cs
void OnCollision(Collider other) {
  if (other.tag == "Wood")  other.GetComponent<Wood>().Burn();
  if (other.tag == "Oil")   other.GetComponent<Oil>().Ignite();
  if (other.tag == "Grass") ...
}
// Lava.cs、Torch.cs、Explosion.cs 里再各抄一遍这张名单

加一种"纸"，要打开每一个火源脚本各补一行：工作量 = 火源数 × 材质数，漏一处就是"火把点不着纸但火球能"。

Noita 的写法——材质只是一行数字，火系统全游戏只有一段：

// 材质表(materials.xml 抽出来的)
mats[WOOD]  = { burnable: 1, autoignition: 300, fireHp: 80 }
mats[OIL]   = { burnable: 1, autoignition: 100 }
mats[STONE] = { burnable: 0 }

// 火系统:唯一的点火代码。有 if,但判的是属性,不是名字
for (const n of neighbors(fireCell)) {
  const m = mats[grid[n]]
  if (m.burnable && m.autoignition <= mats[grid[fireCell]].fireTemp) ignite(n)
}

火球、熔岩、火把都不需要知道木头存在——它们只是往格子里写一个"火"材质，火自带 fireTemp。加"纸" = 材质表加一行，零代码。

反应表更进一步，把 if 变成查表：

// 加载时:328 条标签规则 → 展开成 N×N 查表
for (const r of reactions)
  for (const a of matsWithTag(r.tagA))
    for (const b of matsWithTag(r.tagB))
      rx[a * N + b] = { outA: r.outA(a), outB: r.outB(b), prob: r.prob }

// 运行时:两格相邻,一次数组下标,连分支都没有
const r = rx[grid[i] * N + grid[j]]
if (r && rand() < r.prob) { grid[i] = r.outA; grid[j] = r.outB }

法术同一招：卡不是带脚本的 prefab，而是一串数据操作 [{field:'speed_multiplier', op:'mul', v:2.5}, …]，一个通用解释器按顺序作用到 Config 上。 修饰卡不知道任何弹丸的存在，弹丸也不知道任何修饰的存在，它们只通过 Config 这一个中间物见面；枚举写法里"加速"要分别适配火球、箭、锯刃，又是 N × M。

回到 Unity：prefab 不是问题，问题是逻辑写在 prefab 里的 if 名字。同样的事用 ScriptableObject 完全能做：一个 MaterialDef（属性表）、一个 ReactionTable、一个通用 FireSystem、一个通用 Projectile 吃 ProjectileConfig。 prefab 数量 ≈ 每种类型一个，不是每个东西一个——火球和箭是同一个 prefab、不同的 config。

生活比喻 枚举像给每个员工单独写一份规章（"张三迟到扣 50，李四迟到扣 50……"）；组合像写一条"迟到扣 50"再给每个人填一张考勤卡。人越多，前者越写不完，后者只是多印一张卡。
一句话与代价

枚举 = 每个东西一份代码；组合 = 每个东西一行数据 + 每类东西一份代码。东西的数量远多于类型时（469 种材质 vs 4 种 cell_type，482 张卡 vs 5 种卡类型），后者少一两个量级的代码，且新增内容不碰代码。 代价是涌现出来的组合没法逐个测，所以 Noita 要在规则上加护栏——比如 speed_multiplier 被 clamp 到 0~20，不然叠几张加速就飞出世界。

追问：那"被点燃"这个效果本身，是不是写死在代码里的？

是的，而且必须是。效果（动词）写死在代码里，且很少；数据决定的是谁、什么条件、变成什么、多快（名词 + 条件 + 参数）。把"被点燃"拆开：

层是什么在哪
动词这一格燃烧进度 +1，到头换成 fire 格（可选冒烟）代码，全游戏一份
条件burnable && autoignition ≤ fireTemp代码里唯一的 if，判属性
名词 / 参数谁可燃、燃点、烧多久（fire_hp）、冒不冒烟、火多热materials.xml，每种材质一行

反应表更明显：rx[a*N+b] 确实是个 map，但 map 的值不是函数，是两个材质 id 和一个概率；执行"把两格换成别的材质"的代码永远是同一段。328 条规则 = 1 个动词 × 328 组参数。 整个材质模拟的动词就这么几个：落 / 流 / 飘（按 cell_type 选）、烧、寿命到期、两格反应——469 种材质全是它们的参数组合。实体组件同理：约 200 种 Component 每种是引擎里写死的一套行为，xml 只挑用哪几个、填什么数。

所以"数据驱动"不是"没有代码"，而是代码负责动词，数据负责名词和参数；动词要少而正交，名词可以无限加。判断一个系统设计对没对，就看"加一个新东西要不要新动词"——大多数时候不要，就对了。想要"点燃后变金子"这种新动词，那还是得写代码。

1 · 材质与元胞自动机 materials.xml · CellSim

核心世界是一张材质格子表，每帧按邻居规则挪一挪

原版怎么设计

materials.xml 里 469 种材质，每种只是一行属性：cell_type（solid / liquid / gas / fire）、liquid_sand（是粉末还是液体）、density 密度、 liquid_gravity / liquid_viscosity、burnable / fire_hp / autoignition_temperature / temperature_of_fire / requires_oxygen、durability / hp（爆炸挖不挖得动）、 electrical_conductivity（金属 1、油 0，液体缺省导电）、platform_type（0 = 人能穿过去，树 / 尸块就是 0）、还有一串标签 [water] [burnable] [corrodible] [meltable]……

328 条 <Reaction> 写的是"相邻两格按概率变成什么"，而且用标签当通配符：[meltable] + lava → [meltable]_molten 一条规则管所有能熔的东西； [evaporable_fast] + air → air + air（45%/帧）让激光渣几帧就蒸发。模拟本身是最经典的落沙自动机：自下而上、左右交替扫，沙往下 / 斜下掉，液体还能横着摊，气往上飘，火要氧气、有寿命、点燃比自己燃点低的邻居。

性能靠"只算会动的"：GDC 演讲里讲的每个区块一块脏矩形 + 多线程棋盘格分四轮更新（相邻块不同时算）；新生成的区块是静止的，碰一下才醒。

元胞自动机（落沙游戏）脏矩形 / 睡眠块棋盘格多线程标签系统 + 反应表数据表驱动
生活比喻 每个格子像小区里一户人家，只看左邻右舍、楼上楼下，不知道整个城市长什么样——但"每家只管自己门口"加起来，整个城市就有了交通流。 反应表像化学课本最后那张"哪两样放一起会怎样"的表；"睡眠块"像一整栋没人的楼，物业根本不去巡。
我们复刻时踩的坑
  • 只模拟视口 + 24px 时，手机上子弹飞出屏幕炸出来的地形要走过去才开始动；改成模拟视口 ± 512px 一圈（3×3 ~ 4×4 区块）+ 32×32 睡眠块，模拟从 1.5~4.5ms 降到 0.1~0.9ms。
  • "和空气的反应"被我们跳过了、液体停下就睡 → 激光渣永远留在地上；原版里还会起反应的格子是不能睡的。
  • 用 solid_static_type 判"人能不能站"是错的，platform_type 才是；结果人被树"挂"住、踩在尸块上。
对我们做游戏的启发
  • 用属性代替名字：不要写 if (mat == 'oil')，写"可燃的液体"。新材质只加一行数据，所有规则自动生效。
  • 规则要少而正交：重力、密度、燃点、反应四件事，能推出"熔岩遇水成石头冒蒸汽""油浮在水上烧"这些没人专门写过的场面。
  • 性能不是靠加速算法，而是不算不动的东西：睡眠 / 脏矩形 / 分块，这套在任何模拟类玩法里都能用。

2 · 世界生成 biome_map · wang 砖 · 布景 · 材质带

分层一张小图定群系，一套瓷砖拼地形，颜色当指令放东西

原版怎么设计
  1. 群系图 biome_map.png：一个像素 = 一个 512×512 区块，像素颜色查 _biomes_all.xml 得到群系（煤矿 / 圣山 / 挖掘场 / 雪窟……）。整张地下世界就是几十×几十个像素。
  2. wang 砖：每个群系一张人字形（herringbone）砖库 png，用 stb_herringbone_wang_tile 的算法把边缘颜色能对上的砖拼成一片；拼坏了最多重掷 99 次。砖里的白 / 灰像素是"这里要填材质"，特殊颜色是标记。
  3. 材质带：砖里的白块按群系 xml 的 MaterialComponent 用噪声分成 soil → sand → rock 等带，煤 / 金这种稀有材质只在噪声落在某区间时出现。
  4. 布景（pixel scene）：标记色 → lua 的 RegisterSpawnFunction → LoadRandomPixelScene 从池子里挑一张手绘 png（材质图 + 手绘层 + 背景层三张一组）盖上去；生成点用 spawn_small_enemies / spawn_lamp / spawn_props 这类函数按权重表掷骰放怪、放灯、放箱子。
  5. 整图群系：出生的山体、圣山不是砖，是 init() 里按固定坐标放整张图。

所有随机来自 NollaPrng（MINSTD）——种子 + 坐标派生，所以同一个种子在任何机器上生成的地图逐像素一样，连油罐放在哪、灯是不是空掷都一样。

Wang tiles / 人字形砖值噪声 / simplex坐标派生 PRNG预制件（prefab）"颜色即指令"的小 DSL图片当数据
生活比喻 铺瓷砖的师傅手里一箩筐花砖，规矩只有一条：相邻两块砖边上的花纹得接得上——铺完自然是一整片连贯的图案，师傅自己也不知道最后长什么样。 建筑图纸上红点是灭火器、蓝点是插座：美术在砖上点一个特定颜色的像素，就是在图纸上做标注，程序照标注放东西。
我们复刻时踩的坑
  • PNG 必须自己解码：浏览器 <img> 的色彩管理会把标记色 #000042 读歪，煤矿入口井被封死，每次都重掷 99 次。
  • 世界像素 → wang 像素是半格取整 floor((x+5)/10)，改对后和真实存档的一致率从 82% 到 91%。
  • 地表不能有 45° 以上的坡：soil / grass 是落沙，会被自动机塌成三角堆，用户截图里的"金字塔"就是这么来的。
对我们做游戏的启发
  • 让美术直接画关卡：一张 png 既是形状又是逻辑，不用再做关卡编辑器。
  • 随机要可复现：所有随机从（种子, 坐标）派生，bug 才能复现、存档才能只存差异、玩家才能分享种子。
  • 分层生成：粗图定大结构 → 砖定通路 → 噪声定材质 → 布景定细节，每层都能单独验收。

3 · 区块流式与存档 512×512 chunk · 只存改动

无缝玩家走到哪就算到哪，没动过的一律不存

原版怎么设计

世界切成 512×512 的区块，玩家周围一片（约 3×3）常驻并参与模拟，远了就卸掉。存档目录里只有 world_X_Y.png_petri——被玩家改过（挖、炸、流过液体）的区块才写盘， 没动过的区块因为生成是确定性的，回来重新算一遍就一模一样。区块卸载时里面的怪也一起丢掉，再回来按生成表重刷。

这是"中途永远不出加载页"的根本原因：不是加载得快，是大部分东西根本不用加载。

分块（chunking）LRU 缓存增量存档（delta save）RLE 压缩Worker / 多线程生成按移动方向预取
生活比喻 你家的房间不用每天拍照存档，只要记住"今天挪了哪把椅子"，别的东西回来还在原位。图书馆也不记录每本书的位置，只记"借出去的那几本"。
我们复刻时的做法
  • 生成 + 渲染全放 Worker，主线程只贴位图；同时在飞的请求 ≤ 2、每帧最多收 2 块。手机模拟 CPU ×6 仍 60fps，iPhone 实测区块到达 p95 53ms。
  • 改过的区块用 RLE 压进 IndexedDB（512KB → 几十 KB），真机上出现过 LRU 抖动（20 秒请求 1499 次），用"本帧要用的不卸 + 超缓存先砍预取"堵死。
对我们做游戏的启发
  • 确定性生成 + 只存差异 = 无限世界几乎零存档成本，这条对任何程序化世界都成立。
  • 把"卡"拆成可量化的两件事：主线程帧时间 与 区块到达延迟，分别有判据（p95 ≤ 33ms / 黑洞帧 < 3%），而不是凭感觉说"有点卡"。

4 · 实体 = 组件表 entities/*.xml · Base 继承 · Lua 钩子

ECS一个怪就是一张零件清单，引擎按零件类型逐个更新

原版怎么设计

每个实体是一份 xml，里面一行一个组件：SpriteComponent（帧动画）、HitboxComponent、DamageModelComponent（血量 / 溅什么血 / 哪些材质会伤它 / 着火概率 / 憋气 7 秒 / 摔落伤害）、 CharacterDataComponent + CharacterPlatformingComponent（和玩家同一套行走模型）、AnimalAIComponent、PathFindingComponent、GenomeDataComponent（阵营）、ItemChestComponent（死亡掉落）、 LuaComponent（在 死亡 / 受伤 / 刚体被打缺像素 等事件上挂脚本）、VariableStorageComponent（给脚本存变量）……

316 个生物 xml 里 DamageModel 出现 251 次、AnimalAI 157 次、CharacterPlatforming 133 次。复用靠 <Base file="base_humanoid.xml">：先拿基础模板，块内覆盖、块外追加。 引擎组件的全部字段和默认值都写在 component_documentation.txt，比如 VelocityComponent 不写就是 gravity 400 / air_friction 0.55 / terminal 1000——我们一开始当成 0，手雷石子全不掉。

Entity-Component（数据导向）原型继承（Base file）脚本钩子（Lua）默认值文档化
生活比喻 一份简历表：姓名、学历、技能、健康状况各一栏，HR 按栏目处理，不关心你是谁。Base file 像"基础套餐 + 加料"——僵尸 = 人形基础包 + 弱血量 + 近战；矿工 = 同一个基础包 + 扔炸药。
对我们做游戏的启发
  • 怪和玩家共用运动组件：手感一致、bug 一致、关卡对双方公平——怪能跳的台阶玩家也能跳。
  • 引擎做通用系统，特殊行为交给脚本：黑洞、电、寻路是引擎的；"矿工死了掉金子""巢每 121 帧吐一只"是几十行 lua。
  • 把默认值写成文档比写在代码注释里值钱得多——十年后你自己都会忘。

5 · 像素刚体 PhysicsImageShape · Box2D · 醒着 / 睡着两种身份

融合一只木箱既是一个 Box2D 物体，也是一堆木头像素

原版怎么设计

PhysicsImageShapeComponent：一张 png 就是形状 + 材质，图里每个像素在世界里是一格该材质（wood_prop / metal_rust_barrel / glass_box2d…）。 GDC 演讲里的做法：图 → marching squares 描轮廓 → Douglas-Peucker 简化 → 三角化 → Box2D 刚体；刚体每帧把自己的像素写进世界格子，所以元胞自动机能烧它、酸能蚀它、子弹能抠掉它一角，抠掉后轮廓重算。

再叠几个组件就是全部道具：ExplodeOnDamageComponent（炸药箱被打掉 4% 像素就炸，physics_body_destruction_required 0.04）、MaterialInventoryComponent（油桶装 300 油，被打有概率漏）、 PhysicsJointComponent（nail_to_wall 钉在墙上的轮子、吊链）、PhysicsBodyCollisionDamage（灯笼掉下来砸地就碎）。材质自身还带 solid_on_sleep_convert（崩塌混凝土睡着变静态）、solid_on_collision_explode。

尸体也是这套：ragdoll_filenames_file 里每张 png 一块 meat 刚体，最后化成一堆肉像素。

Box2DMarching squares多边形简化 / 三角化刚体睡眠浮力按密度连续物理 ↔ 离散格子的交接
生活比喻 一块冰扔进水里：飘着的时候是"一块冰"，化了以后就是"水的一部分"。木箱醒着时是一件家具，睡着后就是墙的一部分，火照样能烧到它；有人推一下又变回家具。
我们复刻时的做法与坑
  • 没用 Box2D：醒着自己积分，边缘像素撞地形给冲量 / 摩擦 / 扭矩；睡着写进 chunk.mat 交给自动机，支撑没了再醒。
  • 桌子"穿地"：法线用"接触点质心 → 刚体中心"算，桌面像素多桌腿少，质心偏上 → 算出朝下的法线一路推穿。改成"接触质心 → 边缘像素质心"才对。
  • 小尸块乱转：3~10 像素的碎肉惯量极小，点接触扭矩甩到 20+ rad/s；n<12 的一律按面接触、角速度封顶。
对我们做游戏的启发
  • 两个系统（连续物理 / 离散格子）之间要有明确的交接协议：醒着谁管、睡着谁管、什么时候换手。含糊就会出现"既是又不是"的诡异 bug。
  • 道具 = 形状图 + 几行组件，新道具几乎零代码；美术画一张图就能加。

6 · 法杖与法术 gun_actions.lua · gun.lua · 卡牌牌库

组合法杖是一副牌，施法是抽牌，法术是改一份配置的小程序

原版怎么设计

gun_actions.lua 里 482 张卡，类型只有几种：弹丸（PROJECTILE / STATIC）、修饰（MODIFIER）、多重（DRAW_MANY）、材质（MATERIAL）、工具 / 被动。 每张卡的正文就是对一份配置 c（ConfigGunActionInfo：速度倍率、伤害加成、寿命、反弹次数、重力、爆炸半径、后座力、挂载的子实体……）做几行加减乘。

gun.lua 是发牌规则：每次施法抽 actions_per_round 张；抽到修饰就改 c 再多抽一张让右边那张吃到效果；抽到多重 N就再抽 N 张同一发放出； 触发弹先抽一张当载荷挂在弹上，弹死时在撞点放出（可嵌套）。法力不够 / 次数用完的卡弃掉换下一张；牌库抽空 → 充能、洗牌（或不洗）。 法杖本身只有七八个数：容量、每次施放、施法延迟、充能、法力上限 / 恢复、散射、是否洗牌。

反直觉但有效的细节：c 是每个 shot 一份，所以同一发里所有弹共享最终配置；后座力直接减射手速度——朝下打"后座力"卡每发 +200 px/s 向上，玩家就这么浮空。

牌库机制（Dominion / Slay the Spire 同源）操作序列解释器组合式原语lua 小 DSL顺序即语义
生活比喻 做菜：主料（弹丸）、调料（修饰：辣一点、快一点）、"接下来两样一起下锅"（多重）、"炸完再撒葱花"（触发弹）。调料永远作用在它右边那道菜上，顺序摆错味道就变。 菜谱只有几十种基本动作，菜却做不完。
我们复刻时踩的坑
  • 曾经做成"点一下把杖里全部卡一起放出"，用户一句话纠正："它是一个法杖多个效果，是组合，比如多重是多个弹。"—— 于是照 gun.lua 逐条重写抽牌。
  • 激光其实不是"激光"：就是一发普通弹，air_friction −9（每帧 ×1.15 加速）被 terminal_velocity 1000 截住。数据对了效果自然对，不用专门写。
对我们做游戏的启发
  • 少量正交原语 + 一条组合规则 = 无穷深度。设计 5 种类型、1 页发牌规则，胜过手写 500 个技能。
  • 规则要能被玩家推理："修饰改右边那张"这一条就足够让人自己琢磨出连招，不需要教程。
  • 内容量靠系统而不是靠手写：新法术 = 几行 lua 改配置，不需要程序介入。

7 · 弹丸与爆炸 projectiles/deck/*.xml · ExplosionFactory（反自 exe）

原版怎么设计

网格射线（DDA）能量预算模型hitbox 采样粒子系统additive 混合 / 发光震屏 / 闪光
生活比喻 爆炸像一盏 360° 的手电筒：光照到哪儿哪儿就坏，被墙挡住的地方一点事没有。"能量预算"像挖坑的力气：挖土一铲子一大块，凿石头一铲子只掉一点粉，力气用完就停。
我们复刻时踩的坑
  • 黑洞改了四遍：先当贴图、再当"一口吞掉圈内"、再按 wiki gif 取色、最后反汇编发现是"每帧一条射线 + 16 条扇面射线最多啃 17 格、吃掉的格切向甩出绕圈"。拿不准就反 exe，别猜。
  • velocity_sets_scale 文档原话是"精灵宽度 = 这一帧走过的距离"，我们按速度拉长又压扁，分裂弹被拉成椭圆条。只拉长不压扁才对。
对我们做游戏的启发
  • 能量预算比距离衰减更真实也更好调：一个数（材质 hp）同时决定了挖不挖得动、挡不挡得住。
  • 反直觉但一致的规则玩家学得会：躲墙后免伤这条规则从没写在教程里，但每个玩家都掌握了。

  • 怪"卡在节点原地蹦"：8px 格寻路只采格心一个像素、跳边最多 3 格但跳速只够 13px——路说能上、身体上不去。改成"整个碰撞盒放得下才算能站"+ 按 pixel_gravity 反算抛物线，才不骗自己。
  • 怪"穿墙冒出来"：卡在实心里就每帧往上顶 16px 的兜底逻辑，被沙埋住的怪一帧穿过头顶石板。改成 ±3px 挪不出就原地不动。

对我们做游戏的启发
  • AI 从数据抽，不写 if：几十种怪共用一套代码，差别全在表里。
  • 死亡是物理事件而不是消失动画：血能灭火、肉能被吃、金子能被熔岩吞——尸体继续参与世界。
  • 兜底逻辑最危险："卡住就往上顶一下"这种小聪明，是 80% 穿墙 bug 的来源。

9 · 状态与沾污 SpriteStains · status_list.lua · materials_that_damage

推导状态不是"被赋予"的，是从"身上沾了什么"推出来的

原版怎么设计

标签系统计时器 / 叠加数据表状态可视化（染色精灵）
生活比喻 淋过雨的衣服点不着，得先烤干才会烧；沾了油的抹布一碰火就着、还烧得久；踩过泥的鞋子走一走就干净了。你不需要一个"防火 buff"，你只需要真的是湿的。
我们复刻时踩的坑
  • 湿身碰火"要有个过程"：之前 WET 是个 10 秒计时器，改成 0~10 的沾污量——泡水 0.25s 沾满，站着 80s 干、跑着 10s，碰火每秒烤掉 4 成、烤光才点着；满湿站火里 3.4s 零伤害。
  • 着火伤害按 wiki 是 2% 最大血 / 秒，我们原来 0.2 / 0.5s 是 5 倍。
对我们做游戏的启发
  • 状态由世界事实推出，而不是脚本赋予：这样状态天然和环境互动（下水灭火、油桶漏了溅一身），也天然公平（怪也会湿）。
  • 把状态画在身上（衣服颜色、头顶图标 + 剩余量条），玩家不用看文字就知道自己现在"能不能碰火"。

四层证据，按可信度排
  1. 解包数据：data.wak → xml / lua / png。材质、实体、法术、群系表全部脚本抽成 json（noita-prepare-*.mjs），代码里不出现魔法数。
  2. 引擎文档：component_documentation.txt 列了每个引擎组件的字段和默认值——黑洞 damage_amount 0.1、电 energy 1000 / speed 32 都是从这儿来的，之前倒推的数全被它纠正。
  3. 存档真值：真游戏存档解出来的 24 个区块，逐像素对照（wang 层实 / 空一致率 91.4%，布景坐标 10/10 一致）。
  4. 反汇编：noita_dev.exe 比正式版多留断言字符串（源文件名 blackhole_system.cpp / explosion_factory.cpp），找到引用字符串的函数 → 反汇编 → 抽浮点常量和调用。爆炸 360 条射线、黑洞 17 格 / 帧、追踪弹公式、后座力直接减速度，全是这么来的。

最后一层是 wiki 的演示 gif 抽帧放大取色——黑洞本体是暗紫黑近不透明的圆盘 + 1px 粉边，不是"粉色的"。

生活比喻 修一台老钟：先看说明书（xml / 文档），再对着一台完好的同款钟比零件（存档真值），实在不懂就把机芯拆开看齿轮（反汇编）。凭感觉"应该差不多"装回去的钟，一定走不准。
对我们做游戏的启发
  • 每一小步都可验证：每个子系统一个 Playwright 探针，输出数字（格数 / 血量 / 帧时间）和截图，"感觉对了"不算对。
  • 先查再问：用户的每条反馈先回到原版数据里找依据，再决定改什么；改错方向的成本比多查十分钟高得多。
  • 事故也要记：用 shell 重写文件把 UTF-8 中文全写坏、从编辑器本地历史恢复的那次，被写进文档变成"改源码只用编辑工具"的规矩。

对我们做游戏的十条启发

  1. 先定一个"物理层"，让所有玩法都从它长出来。 Noita 是材质格子；我们的游戏可以是别的东西（一张地图、一套经济、一个社交图），但要有一个所有系统共用的真实底座，而不是一堆各自为政的脚本。
  2. 用属性代替名字。 规则写给"可燃的液体"，不写给"油"。新内容 = 加一行数据。
  3. 少量正交规则相乘，胜过大量手写内容。 法术 5 种类型 + 1 页发牌规则，玩家玩了几千小时还在发现新组合。
  4. 随机必须可复现。 种子 + 坐标派生一切随机，bug 能复现、存档能只存差异、玩家能分享。
  5. 性能靠"不算不动的"，不靠"算得更快"。 睡眠、脏矩形、分块、Worker，这四件事解决了 90% 的卡。
  6. 玩家和怪共用一套身体。 手感一致、关卡公平、状态公平，代码还少一半。
  7. 死亡、受伤、作弊检测都是世界事件，不是脚本判定。 血会流、尸体会烧、偷东西是"货出了框"，于是玩家想的是"怎么骗过世界"而不是"怎么骗过程序"。
  8. 反直觉但一致的规则，玩家学得会。 躲墙后爆炸免伤、后座力浮空、湿身防火——从没写进教程，人人都掌握。
  9. 系统再好，没有引导等于没做。 用户一句"玩不明白"，比任何技术难题都致命。目标箭头、新手引导、暂停里的按键表，都是必需品。
  10. 数值只从数据抽，拿不准就反，每一小步可验证。 这条对做游戏和对复刻游戏一样成立：凭感觉"差不多"的东西，最后都要重做。
